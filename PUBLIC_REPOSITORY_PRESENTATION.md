# DPN Technology Public Repository Presentation Standard

Public-facing repositories should explain what the project is, what exists now, how it is built, how to evaluate it, and what its limitations are.

## Recommended order

1. DPN/product hero
2. Live repository metadata
3. Product capability visual
4. Short product statement
5. Architecture
6. Feature matrix
7. Real visual evidence
8. Install/run path
9. Security/architecture/release resources
10. Maturity and limitations
11. DPN ecosystem navigation

## Status language

Prefer concrete maturity terms:

- Concept
- Prototype
- Development
- Preview
- Release
- Archived

Avoid vague or unsupported status claims such as:
- enterprise-ready;
- production-grade;
- fully secure;
- battle-tested;
- certified;
- 100% reliable;

unless there is evidence supporting the claim.

## Screenshots

Use real runtime or project evidence when possible.

If a screenshot is:
- sample data;
- a mockup;
- a render;
- a prototype;
- an architecture visual;

label it accurately.

## README density

A README can be visually rich without becoming unreadable.

Use:
- headings;
- tables;
- collapsible details;
- short explanatory paragraphs;
- visual sections;
- direct links into deeper documentation.

Keep dense implementation details in dedicated docs rather than forcing everything into the landing page.

## DPN theme

Follow [BRAND_SYSTEM.md](BRAND_SYSTEM.md). Public repository visuals should feel recognizably DPN while preserving product-specific identity.
